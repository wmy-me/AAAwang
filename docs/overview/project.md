# 项目定位与主线

更新日期：2026-11-02。以下是产品目标和当前讨论口径；实现状态以 [当前进度](../progress.md) 和源码为准。

## 项目是什么

生活采买智能体是一个以采买为核心、通过自然语言帮助用户发现信息、比较候选和形成生活服务方案的多智能体系统。React 网页优先，Python 是主体，Android 保留为后续扩展。

用户描述情景、用途、预算、人数、时间、位置与偏好，系统按需追问，调用外部工具和投稿知识库，形成有来源、可比较、可修改的结构化结果。当前产品范围是查询、推荐和规划；下单、预订、支付保留为后续扩展。

## 用户场景与主线

| 场景 | 用户需要 | 目标结果 |
| --- | --- | --- |
| 日常采买 | 给学生买奖品、聚会采购、生活用品 | 商品组合、数量、预算与购买地点 |
| 天气与穿着 | 按天气、用途和偏好选衣物 | 类别、搭配与候选店铺 |
| 美食和本地发现 | 附近夜宵、小吃街、门店与饮品选择 | 地点、菜单、口味、参考价格及出处 |
| 二手选购 | 预算内筛选合适的二手物品 | 成色、规格、位置与候选比较 |
| 旅游和出差 | 目的地、交通、酒店与每日安排 | 行程、费用估算、关联美食和采买建议 |
| 经营与批量采购 | 为经营活动寻找设备、产品或供应方 | 公开候选、规格比较、适配理由与未知项 |
| 投稿知识 | 用户分享摊位、小吃街与体验 | 审核发布后可被检索并引用的作品 |

共同处理链路是：理解目标 → 提取并补充必要条件 → 选择工具和信息来源 → 保存候选及证据 → 比较与规划 → 用代码校验金额、数量等约束 → 展示方案 → 根据修改重新调整。

简单查询使用必要能力即可；复合需求再委派不同 Agent。每次请求不固定遍历所有模块。采买、旅游与经营采购各自管理预算、位置和状态。

## Java 模拟 MCP 服务的定位

Java 工程用于模拟外部成熟 MCP 服务的能力和交互，验证 Python 主系统的接入、工具发现、调用、错误处理与来源记录。三个目录分别提供购物、出行、本地生活的测试场景；它们不是产品所能接入服务的固定上限。

目标是通过统一的 MCP 客户端及服务配置接入这些模拟服务，后续新增其他 MCP 服务沿用同一条接入路径。Agent 不直接依赖 Java 类、数据库表或固定业务实现；外部工具的字段差异可在适配层处理。兼容性仍需对具体服务的协议、传输、认证和工具定义进行验证，不能承诺所有 MCP 服务都无需适配。

初期 Java 只需提供支撑验证和演示的模拟查询能力，不需要先做成完整商城、外卖或旅游平台。返回结果标注模拟来源；真实公开资料和模拟数据分别展示。Java 当前只有 Spring Boot 骨架，尚无上述 MCP 能力。

## 系统职责

| 部分 | 职责 |
| --- | --- |
| React | 对话、候选、方案、地图和投稿页面；当前只有健康检查页 |
| Python API 与业务模块 | 账号、消息、任务、投稿、偏好、方案与权限 |
| Python Agent 模块 | 主协调、信息发现、采买规划与出行子图 |
| 工具集成层 | 外部 MCP、地图、搜索、知识检索及来源规范化 |
| Worker | 后台运行、取消、恢复与知识同步，和 API 共用一个 Python 工程 |
| PostgreSQL 与文件存储 | 正式业务状态、执行记录、知识与附件 |
| Java 模拟服务 | MCP 接入与领域查询的模拟服务端 |
| Android | 后续复用同一后端，不另做一套 Agent |

主协调理解目标、追问与委派；信息发现负责候选与证据；采买规划负责比较和组合；旅游使用专门子图。预算等精确计算由确定性工具完成。不按每类商品建立一个独立 Agent。

## 首个完整业务案例

“预算 300 元，给学生买奖品。”系统能补问人数、查询候选、组织组合、复算金额、说明出处、展示并保存方案；用户修改人数或预算后得到一致的新结果。

这是第一个验证案例，其他场景继续保留，按依赖逐步接入，不代表删去美食、旅游、二手或经营采购。
