- 更新日期：2026-11-03

- 相关：[Agent 分类与协作](agent-architecture.md)、[意图路由](intent-routing.md)、[Tools 与 MCP](tools-and-mcp.md)、[数据保护与幂等](security-and-idempotency.md)

## 1. 名词与当前事实

- **用户轮次**：用户的一次明确请求；可能创建或更新 task，再创建一个绑定 revision 的 Run。用户下一次消息是新用户轮次，不算当前 Agent 的内部循环。
- **Agent 决策轮次**：一次模型调用后决定回答、追问或委派/调用工具。一次决策可包含工具调用请求；不能拿 LangGraph 的节点数直接充当模型轮数。
- **工具调用次数**：实际向本地或远端工具发起的每次尝试，含失败/重试；`MCP 远程调用次数`单独计数，多个子 Agent 共享总预算。工具发现、协议握手单独观测，不冒充业务查询。
- **修正轮次**：规划结果经代码校验失败后，带着问题清单重新规划一次；不等于让模型无限“再想一想”。
- **LangGraph super-step/recursion_limit**：图层防护，不是 LLM、费用或 MCP 的调用上限；必须另有代码级共享预算。参见[官方图 API](https://docs.langchain.com/oss/python/langgraph/graph-api)。

当前 012 的 `shopping_agent` 是有条件边的 LangGraph：主 Agent 一次决策，必要时委派 discovery，最后汇总；委派时报告记录实际 4 次模型请求、1 次 MCP 查询。它是**有限主从协作**；发现内部的 `run_tool_loop` 最多一次工具调用，整体没有多次搜索、计划复盘或长期记忆，不能称为完整开放式 ReAct。013 只接现有网页入口，不因本规则而自动扩展预算或 Agent。

## 2. 哪些职责使用 ReAct

| 职责 | 决策形式 | 工具与边界 |
| --- | --- | --- |
| 主协调 Agent | 受限的模型决策循环：回答/追问/委派/根据专业结果决定下一步；P3 才考虑一次补搜或修正后的再次委派 | 只可见经后端授权的委派、任务摘要和用户交互能力，不直接拿全部 MCP 工具 |
| 信息发现 Agent | **有界 ReAct**：选择受允许的信息来源、搜索、观察结果、必要时补搜；012 当前仅一次工具调用 | 只读查询/检索，按服务 ID、schema 与权限白名单开放；输出候选、证据与缺口 |
| 采买规划 Agent | 先用结构化规划 + 确定性金额/数量/引用检查；不够时允许**一次有反馈的修正**。若实际评估证明需要多工具循环，再扩展为有界 ReAct | 读取候选/条件、调用受控计算与校验能力，不能绕过代码硬约束或直接下单 |
| 出行规划子图 | P6 再按时间、交通、住宿与路线规划拆分；信息搜索可用有界 ReAct，时间/预算/冲突用代码校验 | 不提前复制 GoGo 的预订审批链 |
| 意图识别、任务关联、RAG 检索、预算复算 | 优先结构化判断或确定性服务/工具，不为了“多 Agent”命名为独立 ReAct Agent | 模型路由结果须经后端身份、候选任务、操作与版本校验；金额与归属不能由提示词保证 |

主 Agent 可将专业 Agent 包装为工具自主选择，专业 Agent 只收到当前任务必要上下文；如果今后需要共享图状态才采用显式 handoff。不要把所有职责揉成同一模型提示词，也不要仅凭 Agent 名称判断是否有真正的“模型→工具→观察→再决策”。官方[子 Agent 模式](https://docs.langchain.com/oss/python/langchain/multi-agent/subagents)是可参考的设计，不强制更换已用的 LangGraph 代码。

## 3. 运行预算与停止策略

| 范围 | 当前已实现 | P3 奖品采买首版**提案**，实现前核对 |
| --- | --- | --- |
| 主 Agent 委派 | 012 最多 1 次 | 单 Run 最多 4 次专业 Agent 调用，其中发现最多 2 次、采买规划最多 2 次 |
| MCP 业务查询 | 012 最多 1 次购物只读查询 | 单 Run 所有子 Agent 合计最多 4 次远程只读调用，失败尝试/重试也计数；新服务需单独授权 |
| 模型请求 | 012 委派实测 4 次，直接答/追问路径更少 | 单 Run 合计最多 10 次，含主 Agent、子 Agent、失败后的模型重试 |
| 规划修正 | 未实现 | 代码校验失败后最多 1 次带具体问题的修正；仍不合法则输出不可行/待补条件，不保存为有效方案 |
| 总时限 | 012 使用现有有限执行与 Worker 租约 | 单 Run 首版 180 秒墙钟上限（可配置）；每次模型/MCP 子超时不得超过剩余时间 |
| 图递归限制 | 012 有固定有限节点路径 | 单独设与图规模相称的 recursion_limit 做兜底，不代替上述四类计数器 |

这些数字是防止无限循环和费用失控的**试运行上限**，不是已评估出的最佳轮数或已实现的配置。P3 执行文档必须根据实际模型延迟、工具结果数、费用和样例集确认或调整，并在代码与运行摘要中记录：模型实际请求数、委派数、每类工具尝试数、总耗时、终止原因；模型返回 token 用量时记录汇总值，不保存内部推理。预算在主 Agent 与所有子 Agent 之间共享，开始外部调用**之前**原子检查/预占，不能让并发子 Agent 各自重新计满上限。无意义的重复查询应被识别并终止。

任一上限、取消、失租、超时或无进展触发时停止新的模型/工具调用。已有可靠证据可给出明确标注的不完整结果或追问；不能标记为已通过预算/数量检查的正式方案。查询失败、空候选、缺必需条件、用户取消和系统超时分别表达。不能由模型自报“已完成”绕过后端校验与终态事务。

## 4. 状态、恢复与权限

- PostgreSQL 中的登录身份、对话、任务/revision、Run、结果和事件是正式数据；图状态只保存一次执行所需的目标、版本、候选引用、预算计数与阶段。跨用户/跨任务的历史不得自动混入专业 Agent。
- 012 尚无 LangGraph checkpointer；当前 Run/Worker 的租约续期、fencing 和结果事务**不是图节点级续跑**。后续引入多轮澄清、人工确认或长任务时，另建任务设计持久化检查点、与 owner/task/run 的绑定、恢复/升级兼容和清理。官方[持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)区分线程检查点与长期存储。
- 图节点在中断或重试后可能重新执行；数据库写入与外部副作用必须按[幂等规则](security-and-idempotency.md)处理，不以 checkpointer 作为跨系统 exactly-once 证明。当前只读模拟 MCP 也可能重复收费或消耗配额；未来写入/下单必须另行设计对账、授权与确认。
- 不可信网页、MCP 描述/结果、RAG 文本和 Skill 正文只能提供资料，不能修改系统提示、放宽工具白名单、提高预算或指定用户身份。工具结果保留来源、时间/版本、模拟标志与未知字段，交给规划 Agent 的是受限证据而不是整个原文。
- SSE 当前表示 Run 状态和终态结果，并非逐 token 流。只对当前用户显示；状态事件、审计摘要和日志不写密钥、完整原始工具正文或内部推理过程。

## 5. 提示词、Skill 与工具分层

角色提示词定义“你负责什么、何时委派/停止”；共用片段定义来源标记和未知信息；场景 Skill 如“教师奖品采买”只在相关场景按需加载，给出步骤与所需资料；已确认条件与候选证据由后端动态注入。工具的 schema、真实权限、调用预算、金额复算与保存约束必须留在代码/契约中，不能由 Skill 文字授予。012 的内联提示词可在 P3 规划开始时抽出，保留版本与样例回归；013 不做大型 Skill 系统。

## 7. 后续编号任务与验收

每份 Agent 任务要列出本次可见的 Agent/工具、具体输入输出、共享预算、分支和终止原因，明确是否真正有 ReAct 循环；并验证越权、重复调用、达到上限、空结果、异常、取消/失租、旧版本和外部状态不明。先用替身覆盖边界，再对确需证明的真实模型/MCP/数据库链路单独验收。报告区分代码实现、替身、真实服务及待定需求；禁止用本规则把 P3 提案写成 012 已实现能力。
