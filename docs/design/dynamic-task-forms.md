# 自然语言任务与动态表单设计

- 更新日期：2026-11-04
- 状态：产品与实现设计方向；当前任务卡仍有固定字段，动态表单尚未实现
- 相关：[意图路由](intent-routing.md)、[Agent 协作](agent-architecture.md)、[数据保护与幂等](security-and-idempotency.md)

## 1. 产品体验

用户从对话表达目标，例如“给同学准备一点毕业礼物”“周末找一家附近餐厅”“想买雨天通勤穿的衣服”。主 Agent 先理解场景、已有任务和用户已说出的条件，再决定直接回答、查询工具、追问或建议用户填写几个字段。网页按本轮需要呈现表单，不让用户在创建任务前先填固定的预算、人数和数量。预算、人数和件数都是可选条件，用户没给时保持未知；只有当前目标的某个可靠操作确实需要它，才追问。

表单是 Agent 的结构化追问界面，也是聊天的另一种输入方式。用户可以直接用自然语言回复。用户填表与发消息产生相同的任务版本和受控执行语义；不用表单也能继续聊天。

## 2. 动态表单契约

主 Agent 可提出一份有限的 UI schema，由后端校验后交给前端渲染。首版控件只包含短文本、数字、金额、日期、单选/多选和地点选择等明确支持的类型。每一项须包含稳定字段 ID、标签、可选项或单位、是否必答、提出原因、数据类型和合法范围。字段 ID、控件类型、候选值及数量限制必须符合后端注册的场景能力和校验规则。模型不能任意生成 HTML/脚本、数据库列、工具权限、支付字段或用户身份字段。

同一目标在不同阶段可提出不同字段。例如用户要“看看毕业礼物思路”可先搜索和给选项；当用户要求“为 25 人生成不超 200 元的购买清单”时，预算和覆盖人数可成为方案硬约束。缺预算可以给不带价格保证的探索建议或询问目标价位，不把未知预算补成默认金额。字段是否必须由当前操作和已知数据决定，不能按业务领域一刀切。

## 3. 任务状态与权限

原始用户表达、Agent 提议的字段、用户确认值、来源与版本分别保存。明确区分用户给出的约束、系统从上下文推断的候选值和模型建议；未确认的推断不能自动成为金额或数量硬条件。旧版本的方案和证据继续绑定旧条件，修改后创建新版本。表单提交要带任务/版本和稳定请求 ID，服务端校验归属、幂等与并发；模型返回仅是建议，不能绕过校验。

当前 `task.goal` 与结构化条件保持 017 的一致性门禁。可变的场景字段优先在受限 JSON 条件或扩展模型中版本化，而不是每来一个字段就建一列；正式字段类型和迁移在实现任务中确定。过去预算/人数/数量固定卡片数据需要兼容读取和转换，不能破坏现有任务。

## 4. Agent、Graph 和工具

主协调基于任务状态选择专业能力，专业 Agent 只看所需字段与获准工具。条件边可以走直答、追问、发现、规划或多能力组合，不把固定表单流程写成每轮必经节点。新增场景通过受信能力注册、字段 schema 与领域适配扩展。模型可建议目标和表单，服务端负责权限、字段类型、预算复算、版本和调用预算。

参考 GoGo 的自主委派、追问与客观校验思路，具体实现沿用本项目 Python/LangGraph 和已验证的 Run/Worker。用固定样例验收“无预算也能先探索”“目标变更后生成新字段”“一句多目标分别追问”“表单和自然语言两种方式都可继续”“不必要的追问不会阻断直答”，并记录无依据约束和错写任务的次数。

## 5. 落地顺序

020 先完成模型能力决策、生产工具交集和共享预算，不把预算/人数/数量当作所有购物请求的必填项。随后单独建立编号任务实现动态表单提议、校验、持久化、前端渲染和旧任务兼容。实施报告需区分固定卡片现状与已通过的动态表单链路；本设计文档不将后者标记为已实现。
