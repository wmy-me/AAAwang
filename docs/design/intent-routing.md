# 意图识别与任务路由设计

- 更新日期：2026-11-02
- 状态：对话设计结论与输出草案，尚未实现
- 定位：主协调 Agent 的入口节点，结合任务上下文做结构化判断
- 相关：[Agent 分工](agent-architecture.md)、[工具执行](tools-and-mcp.md)
- 示例字段不是已发布 API；正式实现时在契约和编号任务中固化

## 1. 识别三个维度

| 维度 | 含义 | 例子 |
| --- | --- | --- |
| 业务领域 | 当前讨论的场景 | 采买、本地生活、出行、经营采购、普通聊天 |
| 操作类型 | 用户要做什么 | 查询、规划、修改条件、补充信息、取消 |
| 任务关联 | 新目标还是已有目标，指向哪个任务 | 新建奖品任务、修改当前奖品人数、指代不明确 |

领域分类不直接等于调用某个 Agent。识别后由主协调按目标与依赖组织能力；RAG 和 MCP 是实现能力，不作为和“采买、旅游”并列的用户业务领域。

## 2. 输入上下文

除当前消息外，提供当前会话的必要最近消息、任务摘要、已确认条件与版本、待回答的问题，以及用户明确选中的卡片或任务。

用户身份与资源范围来自认证上下文，任务候选由后端限定为可访问资源。模型不用选择当前用户，也不从投稿或网页正文推断用户发出了新的操作指令。

任务摘要包含辨认所需的目标、状态和关键条件，避免把全部对话和全部检索资料塞入识别提示词。

## 3. 第一版处理顺序

### 3.1 明确的界面操作

用户点击具体卡片的“修改人数”时，后端已知资源与操作；先校验身份、资源归属、任务状态与版本，再处理。不必让模型重新猜测按钮含义。

### 3.2 明确的待答问题

系统刚问学生人数，用户只回答“25”，优先按人数解析并校验。若回答无法匹配字段或明显转换话题，交给模型判断，不能把所有后续输入强行解释为原问题答案。

### 3.3 一次模型结构化判断

复杂表达、话题切换、多目标和模糊指代由一次结构化判断处理，作为主协调入口节点。首版不强制每条消息都经过“独立查询改写 Agent + 独立识别 Agent + 主 Agent”三次模型调用。

必要的上下文补全可由该次判断产生规范化目标，但保留原文和用户明确条件。未知字段保持未知；不通过改写暗中加入预算或偏好。

### 3.4 后端校验与路由

检查输出 schema、允许操作、目标任务、字段取值、权限、状态与版本。输出是待校验的路由建议，不直接作为数据库写入命令。模型输出无法解析时不能按默认修改或取消操作继续，按任务预算重试或清楚反馈未能识别。

新任务 ID 由服务端创建，已有任务只能从给定候选中选择；任务更新按正式业务规则生成新条件版本，避免旧执行覆盖新结果。

## 4. 输出草案

用户说“奖品人数改成 25 个”，且上下文中能确定奖品任务：

```json
{
  "message_type": "task_request",
  "operations": [
    {
      "domain": "shopping",
      "action": "update",
      "target_task_id": "task_prizes",
      "changes": {
        "recipient_count": 25
      },
      "evidence": "奖品人数改成 25 个"
    }
  ],
  "resolution": "resolved",
  "clarification": null
}
```

`task_prizes` 是示意的后端候选标识，不是模型有权访问任意 ID 的凭据。JSON 中的中文 evidence 为用户原文示意，不是要求输出内部推理。

| 字段 | 作用 |
| --- | --- |
| message_type | 普通聊天、业务请求或待答信息等消息形态 |
| operations | 支持一个消息包含多个目标或操作 |
| domain | shopping、local_life、travel、business_procurement 等候选领域；枚举在契约中确定 |
| action | query、plan、update、provide_info、cancel 等候选操作 |
| target_task_id | 已有任务的候选引用；新任务或指代不明时可空 |
| changes | 用户本次明确提出的字段变化；只允许该场景支持的字段 |
| evidence | 支持判断的用户原文片段，便于排错 |
| resolution | 例如 resolved / ambiguous，用于区分是否存在关键歧义 |
| clarification | 需要用户解决的具体歧义，没有则空 |

“新建任务”由操作目标及 target 的解析结果决定；是否需要新建正式 task 由业务层处理。具体字段校验、枚举及多操作的关联表示在实现任务中确定，不在此假装已有完整协议。

不把模型自报的 `confidence: 0.95` 当成经过校准的正确率。首版优先记录识别依据、候选任务、歧义和实际路由结果；如未来使用分类分数，需要在独立验证集上校准阈值。

## 5. 意图歧义与执行条件缺失分开

“给学生买奖品，预算三百”已经能确定采买规划；缺人数不等于意图不明。

处理方式是关联或建立相应任务、保存已确认预算和用途，再由场景条件检查判断需要人数并生成追问。

| 场景 | 典型条件 |
| --- | --- |
| 奖品组合 | 人数或份数通常影响可行方案 |
| 附近推荐 | 需要确定查询中心，可使用已授权有效位置或询问 |
| 衣物推荐 | 无预算可先给价格档位，不强制阻塞 |
| 出行规划 | 目的地、日期、出发地和人数按本次目标补充 |

已有采买和旅游两个任务时，用户说“预算改成五百”，如果无可靠目标指向，询问具体修改哪个任务。不能只依据“最近活跃的 Agent”直接写入。

## 6. 多意图与话题切换

| 表达 | 预期处理 |
| --- | --- |
| 给学生买奖品，预算三百 | 新采买规划目标；按需追问人数 |
| 附近有什么便宜的夜宵 | 本地生活查询；确定查询中心 |
| 改成二十五个人 | 结合任务上下文定位并提出人数变更 |
| 三天，两个人 | 匹配待回答的出行问题，或在不明确时澄清 |
| 这个先取消，帮我看看杭州酒店 | 分别识别取消与酒店查询，检查“这个”具体指向 |
| 取消订单有什么限制 | 查询规则，不执行取消 |
| 帮我安排杭州三日游，顺便推荐伴手礼 | 出行和采买两个关联目标，不压缩为单一标签 |

多目标由主协调识别依赖：可独立的查询可按条件并行；依赖出行区域或日期的目标等待相关条件。歧义阻塞对应操作，不能把“可能是取消”直接当作授权，也不能把旅游预算自动共享为采买预算。

普通聊天可以直接回复，不强行建立采买任务。取消任务、停止当前执行和未来取消订单是不同操作，必须在正式契约与业务层分别定义。

## 7. 参考 GoGo 的方式

固定提交 [IntentRecognitionRouter](https://github.com/wmy-me/gogo-agent/blob/d7823df02887b01e31ffa094d06ab22653876098/src/main/java/com/gogo/travel/agent/intent/IntentRecognitionRouter.java)采用多意图结构守卫、规则、向量匹配与 LLM 兜底；疑似多意图或跨类歧义交给模型，避免单意图快路径强制截断。

本项目首版只实现“明确交互与上下文规则 → 模型结构化判断 → 代码校验”。积累真实表达与错误样本后，再增加规则或语义样本向量快路径。

不复制 GoGo 的相似度阈值、类别或调用次数。相似度不是分类正确概率；阈值、类别间分差和回退策略需要用本项目样本确定。向量路由与投稿 RAG 的语料和索引用途不同，不混作一个知识库。

## 8. 评估与实施时机

准备带预期领域、操作、任务关联、字段变化和澄清要求的测试集，覆盖：

- 明确新任务、简短回答和修改条件。
- 同一会话多任务、跨话题、模糊指代。
- 一句多目标、顺承依赖、取消加新查询。
- 讨论某操作规则而非执行操作。
- 普通聊天、非法参数、不支持场景和结构化输出失败。

记录任务关联准确率、操作识别准确率、字段提取准确率、错误写入或取消次数、不必要追问次数、耗时和模型成本。领域分类正确但改错任务仍属失败。

003 先验证最小工具调用；具备任务上下文与资源隔离后再落地完整识别与路由，不因保存本文就提前建立全部 Agent。实施前另建范围明确的执行文档。
