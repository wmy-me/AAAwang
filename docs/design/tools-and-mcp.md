# Tools 分类与 MCP 接入设计

- 更新日期：2026-11-02
- 状态：对话设计结论；工具管理与 MCP 当前未实现
- 相关：[Agent 协作](agent-architecture.md)、[意图识别](intent-routing.md)、[知识检索](rag-and-retrieval.md)
- 当前执行范围仍由用户指定的 [编号任务](../vibe%20coding/README.md)确定，本文不替代具体任务

## 1. 两个分类维度

工具按业务职责组织，接入方式另行记录。

| 职责组 | 例子 | 主要使用者 |
| --- | --- | --- |
| 信息查询 | 商品、门店、酒店、交通、地图、天气、联网搜索 | 信息发现、出行 |
| 知识检索 | 搜索投稿、读取作品与原文证据 | 信息发现 |
| 规划计算 | 数量分配、金额复算、日程与路线检查 | 采买规划、出行 |
| 任务上下文 | 条件、候选、已有方案与偏好读取 | 主协调及专业 Agent |
| 用户交互 | 补充条件、确认条件调整 | 主协调 |
| 业务操作 | 保存方案、收藏和投稿等 | 获授权的业务入口 |

实现来源包括本地 Python 函数、应用服务、外部 HTTP API、MCP 服务或检索服务。MCP 是接入方式，不是独立业务领域；预算计算不必包装成 MCP，天气工具也可能由 MCP 提供。

业务操作不等于向模型开放所有业务接口。首次实现时逐项确定哪些适合作为 Agent 工具；权限与写入校验保留在业务服务中。下单和支付不注册为当前可用能力。

## 2. 统一工具入口与按需可见性

设计统一的工具描述和调用入口，至少记录：

| 元数据 | 用途 |
| --- | --- |
| 内部工具标识、名称、描述与输入 schema | 说明用途并校验输入 |
| 来源方式、服务 ID、原始工具名 | 标识远程工具和处理同名冲突 |
| 能力组、允许 Agent 与任务类型 | 构建当前任务的可见工具子集 |
| 超时、调用预算、重试策略 | 约束执行成本与期限 |
| 读写性质、访问规则 | 决定允许执行的操作 |
| 数据来源类型 | 区分模拟目录、公开信息、用户投稿 |
| 结果与错误处理方式 | 保留调用事实并规范化必要领域字段 |

主协调优先获得委派、上下文和追问能力；信息发现获得查询与检索；规划获得候选读取、计算、校验及发起补搜请求的能力。不把全部远程工具一次性注入每个 Agent。

本地注册的委派工具与预算函数可共用调用管理机制，但不必经过网络传输。调用预算由任务与所有子 Agent 共享。

## 3. 执行边界

- 用户身份和资源访问范围从后端认证上下文注入，不接受模型传入的用户身份作为授权依据。
- 工具执行前做 schema、权限、当前任务版本和状态检查；执行后保存结果或引用与必要审计信息。
- 远程工具描述、网页与投稿正文都是外部数据，不能改变系统权限或指定新的用户身份。
- read-only 等工具声明用于描述能力，实际只读性仍需注册策略和服务端行为保证。
- 参数错误、超时、协议错误、远程执行失败与正常无匹配结果分别表达；失败不转换成伪造成功。
- 重试按工具性质和期限设计；未来写操作不能沿用任意自动重试。
- 记录必要的输入摘要、耗时、状态与来源；密钥、认证头和不必要的个人数据不进入日志。

## 4. MCP 分两层接入

| 层 | 负责 | 不应负责 |
| --- | --- | --- |
| 协议客户端层 | 配置、认证、连接、初始化、工具发现与调用、生命周期、超时 | 硬编码某个商品或酒店结果结构 |
| 领域适配层 | 将必要结果转换为商品、地点、交通酒店等候选，绑定来源和证据 | 重新实现另一套 MCP 连接逻辑 |

接入流程：

1. 从受信后端配置选择服务 ID、地址、传输与认证信息。
2. 使用所选 SDK 建立连接并完成协议初始化。
3. 发现工具，保留原始名称、描述和输入 schema，处理发现分页。
4. 按本项目策略选择工具，再提供给当前任务和 Agent。
5. 使用来源服务及原始工具名路由调用，校验结果与错误标志。
6. 保存必要原始结果与证据；需要规划时再转换为领域候选。

发现不等于自动允许调用。发现 schema 与模型工具接口不完全兼容时做明确适配或拒绝注册，不静默删除约束。schema 转换的兼容性在后续模型工具调用任务中验证。

工具身份保留服务 ID 与原始工具名。向模型暴露的别名如受字符或长度限制，使用稳定映射；不能因别名相同调用错服务。

## 5. 两类结果同时保留

协议层保留远程内容块、可用的结构化结果、工具错误标志及来源信息；领域层按需规范化：

- 候选 ID、外部资源 ID、平台或服务 ID。
- 商品名称、规格、单位、货币与可获得的价格信息。
- 地点、时间、更新时间和证据引用。
- 来源类型、模拟标记、未知字段与资料限制。

不假定所有 MCP 工具都返回商品 JSON，也不把单个 Java 模拟工具的输出强制套在所有外部服务上。引用必要快照并不是无限保存全部原始返回。

## 6. Java 模拟服务

shopping、travel、local-life 是三类模拟场景，用于验证与演示通用接入。未来增加外部 MCP，应主要增加服务配置、授权配置与必要的领域适配，并进行实际兼容验证。

本项目不承诺任意 MCP 服务无需适配；传输、协议协商、认证和工具定义需要具体核对。初期不建设完整商城、旅游或外卖平台。

002 只验证 Python 与一个 shopping 模拟工具的真实 MCP 连接、发现和调用，不调用模型。之后的工具调用任务验证模型选择工具、生成参数、执行与根据结果回答。

## 7. 当前目录的演进建议

| 目录 | 职责 |
| --- | --- |
| `backend/src/life_agent/tools/mcp/` | 通用 MCP 客户端及服务描述 |
| `tools/maps/`、`tools/search/` | 地图和搜索的必要封装与领域适配，复用已有连接层 |
| `tools/knowledge/` | 封装检索与证据读取 |
| 规划、上下文与工具管理模块 | 具体任务需要时增加；不现在批量生成空目录和空类 |
| `contracts/mcp/` | 本项目模拟工具的具体契约与适配说明 |

API、业务服务和工具各司其职，普通页面请求不必经过模型。所有 Agent 共享同一套正式业务校验。

## 8. 需要的验收

- 本地工具和远程工具经过相同的受信执行边界。
- 未允许的工具不因被发现就暴露给模型。
- 两个来源的同名工具不会混淆。
- 错误、空结果和模拟数据能够正确区分。
- 服务配置变化复用同一客户端，原始结果与领域结果可追溯。
- 调用超时、异常或取消后清理资源，迟到结果不能覆盖已更新任务。
- 涉及个人资源时加入跨用户访问和缓存隔离验证。
