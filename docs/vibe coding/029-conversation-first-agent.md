## 1. 当前问题与目标

现有网页要求用户先创建购物任务，展示任务目标、物品、预算、人数、数量等输入；聊天发送还依赖已选 task。即便字段可动态生成，也让用户负责整理结构化条件，与当前明确要求不符。

构建 GPT 风格对话主入口：用户登录后新建对话、输入自然语言，即可得到助理消息。Agent 自行根据对话与任务上下文理解目标，判断直答、按需追问、授权工具/专业能力及结果汇总。用户只需在聊天中表达和回答；不要求手动创建任务、填写目标卡、预算人数数量或动态表单，不将“填写表单”作为进入或继续任务的前提。模型无足够信息时自然语言追问；无预算等也可先探索，不把未知值默认为 0。查询完成后给出可阅读的自然语言总结、已知/未知和可追溯来源。

## 3. 必须完成的端到端能力

1. **对话界面**：默认界面以历史对话、消息区和固定输入框为主；新用户可创建会话并直接发送；发送中、取消、错误和重试可理解。旧工作台、动态表单不再出现在默认聊天流程，也不能成为隐藏的必经步骤。后端历史接口与数据保留兼容。
2. **服务端对话入口**：针对已认证用户的 conversation + message 创建幂等回合，支持新会话无预先 task；由服务端/模型受控决定是否需要在后台创建或关联任务。明确请求 ID、会话归属、事务、并发、消息与 Run 的绑定；重复提交不重复创建回合。闲聊可直答，不为每条消息强制创建购物任务或调用外部工具。返回/存储的 assistant 消息可刷新重读。
3. **连续对话与条件**：只有当前用户消息、已确认上下文与合适的历史才可用于任务；用户说“预算 180、25 人”时自动提取并版本化，后续“改成 150”作为新用户明确指示更新当前任务快照，旧 Run 与条件仍可读；任务归属有歧义时先自然语言澄清，不猜或跨任务覆盖。目标/条件冲突沿用既有安全校验并用对话解释，不要求手填卡片。避免把普通问答误改为任务。
4. **Agent 执行与总结**：沿用 coordinator、discovery 和受控工具/Skill 结构，在已有预算和白名单内让模型按需选择；查商品、高德地点/天气、公开搜索等能力按场景选择，不写死顺序或硬编码具体数值。结果在助理对话中汇总，保留公开来源链接、查询时间、模拟商品标记；未知库存、价格、工具错误不能编造。不得将搜索摘要写成已核验网页或实时报价。模型上下文不包含密钥；外部内容不能改变指令或授权。
5. **进度与持久化**：展示可理解的执行状态（如正在查询、已完成、失败/取消），不展示内部思维链。复用现有事件/SSE、独立 Worker、租约/fencing、共享预算和取消机制；只为有意义的结果创建 assistant 消息，避免重复、陈旧 Run 覆盖新版任务。旧会话、任务和历史 Run 仍可读取。涉及数据库变动写 Alembic 迁移和兼容策略。
6. **拒绝额外范围**：不实现订单、支付、RAG、出行完整业务；不增加表单作为替代对话；不擅自将只读工具变成写操作。

## 4. 验收矩阵

| 场景 | 具体通过标准 |
| --- | --- |
| 新会话即聊天 | 浏览器从新对话直接发送问候/普通问题，真实模型回答，用户和 assistant 消息刷新后仍可读；未要求创建任务或填写卡片。 |
