## 目标

029 会话路由已读取最近 8 条消息，但 Worker 的普通回答主要使用当前输入和条件，用户的连续表述可能在路由阶段被理解，实际回答时却丢失上下文；路由模型还在 API 线程同步调用且不计入 Run 共享预算。本任务统一本次对话回合的短期上下文构建与模型调用预算，使聊天、追问和采买续问真正使用同一用户的相关近期信息。

保持纯对话和按需调用工具；不实现跨会话长期偏好、向量检索、完整 RAG 或图检查点。原始对话持久化与结果卡沿用已有语义。

## 实施范围

1. 建立单一、可测试的短期 ContextBuilder：服务端认证后按 owner/conversation 和当前回合截断点读取有限近期消息，保持顺序和 user/assistant 角色；排除未来消息、跨用户/跨会话、取消/失败残留及重复当前消息。通过数据边界和任务关联检查注入当前相关 task/revision，不能默认取另一个任务；多任务歧义需追问。不要暴露内部思维链。
2. 路由、taskless 直答及购物能力决策使用各自必要的同一上下文视图；专业 Agent 只拿需要的内容。用户明确新输入优先于旧上下文，任务条件只能由已确认的当前 revision 提供，不能从摘要或模型猜测改写预算。模型按需选择直答、追问或已授权工具，不以关键词写死路由或工具顺序。
3. 执行链路中将会话路由模型调用计入同一回合的调用、超时与取消预算：优先把路由纳入现有持久化 Run 和 Worker；如果因数据模型约束采用其他方案，需保证预算预占在路由请求之前、与后续 Run 同一份持久预算、并发及重试不会重置。不能为每条闲聊创建伪购物任务。事务与行锁不能跨网络模型调用持有；幂等重试、取消/租约丢失及失败消息保持一致。
4. 设置可配置的消息数量和总上下文大小限制，按完整对话轮次裁剪，保留当前输入与系统规则；准确 token 计数不可用时采用保守估算并说明。工具调用消息与对应结果不得拆开；不要把截断后的资料当成完整事实。不修改或删除数据库原消息。长历史丢失时明确边界；自动摘要和长期记忆本任务不实现，后续单独推进。
5. 保持卡片与消息/Run 的正确绑定、旧任务 revision、用户隔离、MCP 白名单、动态表单历史及安全配置。若 schema 需要调整，提供 Alembic 升降级与旧数据兼容策略。
