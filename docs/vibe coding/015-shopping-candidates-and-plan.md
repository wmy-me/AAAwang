## 1. 目标与范围

014 已实现选中购物任务的两轮对话、条件版本、真实 Worker/DeepSeek/MCP 查询和助手消息持久化，但第二轮购物查询返回空候选，没有候选表、方案表、金额复算或可刷新查看的正式采买方案。本轮以“教师为 25 名学生采购奖品，总预算 200 元，每人至少一份”为验收场景，让已有购物任务产生有来源的候选快照、经服务端校验的结构化方案和网页展示。用户修改预算或人数后再次执行，应生成基于新条件版本的方案，旧方案仍能按其原版本查看。

首版只使用 shopping-mcp 的只读模拟数据，必须在界面和结果中标记 `simulated`。不实现自动跨任务意图路由、真实平台报价、购物车、订单、支付、投稿、RAG 或出行规划。PDF/Word/Markdown 解析、分块和向量化仍按 P5 的独立任务实施。

## 3. 数据与行为契约

1. **可命中的候选**：为教师奖品场景准备稳定可查询的模拟商品数据，覆盖至少一个满足“25 人、200 元、每人一份”的组合。MCP 返回稳定商品标识、名称、单位价格、币种、包装/可分配份数、来源、模拟标志和可用性说明；缺失报价或规格的商品只能作待核实资料。数据应继续通过现有通用 MCP 接入路径查询，不在 Python 中硬编码候选或金额。查询为空时保持明确的空结果。
2. **候选快照**：后端把每次 Run 实际采用的候选保存为受 owner、task、revision、run 约束的结构化快照，保留来源标识、报价时间或“未知”、规格、原始查询时间和模拟标志。定义候选去重与稳定业务键、必要字段、唯一约束、删除链和迁移。持久化只存规划所需字段，避免重复保存不受控的 MCP 原文或凭据。
3. **规划输出**：增加受限采买规划步骤，输入当前任务条件与同一 Run 的候选快照，输出候选 ID、购买包装数量和必要说明。专业规划步骤可以使用结构化模型输出；主 Agent 决定何时委派，发现 Agent 只提供只读候选。规划只能引用快照中的 ID，不能自行制造商品、价格或已核验来源。按需加载教师奖品场景指引时，提示词和 Skill 不能赋予写库或工具权限。
4. **代码校验**：用 `Decimal` 和明确币种计算数量、商品小计和总价；“每人至少一份”的覆盖数须按包装规格与可分配份数计算。明确运费、税费、优惠等未知项的展示语义，不能把未知项当零并声称最终成交价。校验预算、正整数购买数量、候选归属、规格及来源版本。校验失败可把具体错误交给规划步骤最多修正一次；仍失败则记录失败原因或待补条件，不保存有效方案。接受的方案须由服务端计算并保存校验后的金额，不信任模型报出的合计。
5. **版本与幂等**：方案关联 owner、task、不可变 revision 和 run；同一 run 的重试与 Worker 重新领取不得重复插入候选或有效方案。旧 revision 的迟到 Run 可以按原版本查看，但不得覆盖当前 revision 的方案。取消、失租和 fencing 失败的 Worker 不能写入当前结果或助手成功回复。方案和 Run 终态、关联助手消息保持现有一致性；定义失败/取消时的可重读状态。
6. **读取与网页**：增加受认证保护的候选及方案读取契约，服务端按 owner 与 task/revision 授权。网页沿用 014 工作台展示候选来源、购买数量、覆盖人数、服务端复算总额、预算余量、模拟标志和未知费用提示；刷新后重新读取。修改条件后显式区分旧版与当前版，空候选、预算不足和规划失败有各自说明。
7. **执行预算**：P3 提案为单 Run 最多 10 次模型请求、4 次只读 MCP 业务查询、4 次专业 Agent 委派和 180 秒墙钟。实现时核对实际节点需要，采用贯穿主从 Agent 的共享硬上限，在每次模型/工具尝试前检查并计数，包含失败与重试；最多一次规划修正。记录实际请求、委派、工具尝试、耗时与停止原因。图的 recursion_limit 仅作兜底。可在任务报告中给出经实测调整的更紧上限，不得无界扩容。

## 5. 验收标准

| 场景 | 通过标准 |
| --- | --- |
| 有候选的奖品任务 | 25 人、200 元用真实 DeepSeek → Java 模拟 MCP → Worker → PostgreSQL 完成查询和规划；方案只引用实际候选，人数覆盖和金额可由数据库快照复算，网页刷新可读 |
| 改条件 | 用户修改人数或预算形成新 revision 后重新运行，新旧方案分别绑定各自版本；旧 Run 迟到不能成为当前方案 |
| 空候选与无效规划 | 空结果、预算不足、未知关键报价/规格、伪造候选 ID、数量非法和修正后仍失败均不能保存有效方案，界面说明原因 |
| 并发与权限 | 同一 Run 重试只有一份有效快照/方案；两个账户无法交叉读取；取消/失租/旧 Worker 写入不能覆盖有效结果 |
| 回归与真实性 | 014 对话、旧 Run 与消息路径仍可用；数据库迁移与 `alembic check`、相关 Python/Java 检查、前端 lint/build 通过；报告分别标注真实调用、模拟商品和替身测试 |

若当前真实 DeepSeek、MCP 或数据库不可用，报告明确列出未验收项，不能将替身测试标记为端到端通过。保留用户原有数据，只清理本轮新建的隔离测试数据。完成报告与进度同步后停止，下一编号任务再规划方案调整与更广场景。
