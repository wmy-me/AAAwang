## 目标

在现有纯对话基础上，让 Agent 可以记住用户明确要求保存的长期偏好，并在同一用户的后续会话按需使用。用户可通过自然语言查看、更正或删除记忆。

例如：“记住我不吃辣”→ 系统保存；新建会话询问餐厅时可参考该偏好；“忘记我不吃辣”后不再召回。用户本轮明确要求优先于长期偏好。一次任务的预算、地点和数量默认为本次任务条件，不自动当作长期记忆。

## 开始前

读取根目录 `AGENTS.md`、`CLAUDE.md`、030 报告和上下文设计，核对真实会话、Worker、ContextBuilder、用户认证和 PostgreSQL 模型。检查已有数据库、DeepSeek 和 Worker 的可用性；不显示密钥、不启动备用 Compose、不覆盖或删除用户数据。检查是否已有用户记忆实现，避免重复建设。

## 实施范围

1. **存储**：复用现有 PostgreSQL，按登录用户隔离持久化记忆。包含归属、内容或规范值、来源、创建/更新时间和状态；提供 Alembic 迁移。对重复写入、修改、删除定义清晰语义，原始会话和任务版本不受影响。不引入 Redis、向量数据库、额外外部服务或新的 API Key。
2. **对话驱动**：明确的“记住、查看、修改、忘记”由模型在受控能力中识别并调用服务端接口；用户通过聊天完成操作，不要求手工创建表单。记录成功或失败的自然语言反馈。一般聊天中的推断不静默存为长期记忆；临时任务条件仍归当前 task/revision。
3. **按需召回**：在受认证用户约束下，按当前需求召回有限相关记忆，加入本次上下文；不要每轮发送全部历史记忆。来源内容作为数据，不能修改 system prompt、工具权限或预算。本轮用户明确条件优先于旧偏好；无相关记忆时保持正常回答。保留 030 短期上下文与共享预算。
4. **隐私和隔离**：服务端决定 owner，用户只能读取/修改自己的记忆；默认不保存密钥、密码、证件或支付信息。删除后默认查询/召回不能返回该条。日志不输出凭据或完整敏感内容。外部模型不可自定 user ID 或数据库操作。
5. **结构**：根据现有代码职责适度新增 memory 模块/工具，由 Agent 按需调用；避免硬编码示例句式、强制每条对话走固定记忆流程或增加不必要的空目录。可用受控意图/结构化调用，后端完成权限、类型和幂等校验。
