## 1. 当前事实与目标

015 已保存每个 Run 的候选快照及服务端复算方案，网页可刷新查看。但当前 `build_plan_draft` 在候选中按价格选一款商品，用 `ceil(人数/每包份数)` 算数量；用户尚不能选择另一款、指定购买数量或对已有方案发起可追踪的调整。015 的真实验收中，任务目标仍写“25 名学生”而 REV 2 将人数改为 30，模型先追问冲突。

本轮让用户在**明确选中的购物任务**中调整已生成方案的候选与包装数量，在同一版条件下经后端复算、版本校验后保存新方案版本。新的人数、预算等条件继续走现有 TaskRevision 和新 Run，服务端以明确的最新条件为准，并把目标文字与结构化字段冲突呈现给用户确认，不能悄悄覆盖。保留 015 的自动首版方案及历史 Run 查询路径。

## 3. 行为与数据契约

1. **调整入口**：提供仅针对已登录用户的指定 task、指定基准方案/Run 的方案调整接口。请求包含稳定 `client_request_id`、基准方案版本或 ETag、当前 `expected_revision`、选中的候选 ID 与正整数包装数量。服务端从会话确定 owner，并确认基准 Run 与候选属于同一 owner/task/revision；未知 ID、旧条件、并发修改给出可解释 404/409。前端只传选择与数量，不传可信价格或总额。允许多个商品行，候选不重复；若本轮数据模型只支持单项，先补齐结构以支持多行，不让旧版数据失效。
2. **复算与保存**：复用 015 的 Decimal、币种、可分份数、库存/可用性与未知费用语义，校验每一行的数量、小计、覆盖人数、预算和总额。新增的持久化调整版本引用原始候选快照、基准方案及当前 TaskRevision，记录来源 `manual_adjustment` 和服务端计算结果。不可变历史可按版本读取；同一任务当前展示版本通过事务和版本前提切换，两个并发调整最多一个胜出，旧 Run 的迟到完成不能覆盖当前选择。根据现有 schema 选择新增表或有约束的版本表，用 Alembic 新迁移，不改 0011。
3. **幂等与权限**：同 owner/task 的同一请求 ID 与相同指纹重复提交返回原方案版本，不同实质请求返回 409；提交成功但响应丢失时可安全重试。隔离账户不能读或修改对方候选、方案与调整记录。取消/失租只影响 Run，不能留下半写入调整；不因为页面重试创建重复版本。
4. **条件冲突**：修改人数、预算仍通过现有条件版本入口。区分 `task.goal` 的历史描述和结构化 revision 的权威条件。若新条件与目标文字出现明确矛盾，界面展示冲突并让用户确认或修正目标描述，再启动新 Run；不得在旧方案上修改人数数字伪装成新条件下已验证。冲突判定先用现有可核实字段和有限结构化判定，并记录来源与不确定分支，不能仅靠字符串替换猜用户意图。
5. **网页**：在现有候选/方案面板提供选择商品、编辑包装数量、预览服务端复算结果、提交调整及历史版本切换。明确标注模拟报价、查询时间与未知运费等费用；刷新能读到最新调整和原方案。客户端断线或重复点击沿用同一请求 ID。
6. **Agent 边界**：本轮的手动调整和金额校验是受控业务操作，无需让模型直接写方案。保留原 `shopping_agent` 自动建议及当前 5 次模型请求、1 次 MCP 查询的上限；如果加入自然语言“换成另一款”等辅助解析，需先给候选范围、可选操作和共享预算，解析结果走同一受控调整服务，歧义先追问。本轮不开放外部写工具、下单或支付。
