## 1. 问题与本轮目标

013 的网页要求用户手动创建购物 task/条件，再单独启动 `shopping_agent` Run。现有 `POST /api/conversations/{id}/messages` 只保存用户文本，不触发任务；012 Worker 只把 task 的固定 goal 和条件快照传给主 Agent，结果保存在 `shopping_run_results`，没有助手消息。因此“给学生买奖品 → 系统追问人数 → 用户说 25 人 → 同一任务继续”不能真正走通。

本轮只面向用户**明确选中的购物任务**建立最小自然语言多轮入口。用户在该任务下提交消息后，由服务端关联不可变消息、当前 task/revision 和对应 Run；用户明确补充的 `budget`/`people`/`quantity`/`item` 进入新 revision，`shopping_agent` 同时看到**本轮原始消息**与已确认条件。完成的回答作为当前对话可重读的助手消息，与产生它的 Run 关联。刷新或重启后，仍能看出每一轮的用户消息、任务版本、Run 和助手回复。014 不要求自动跨任务找目标，也不生成正式采买方案。

## 3. 输入输出与执行边界

1. **明确选中任务**：新增一个受认证保护的购物任务对话提交入口（路径/请求 schema 在契约中确定），请求包含稳定的 `client_turn_id`、正文、所选 `task_id`、`expected_revision`。服务端从登录态确定 owner，校验 task 属于该对话及当前用户。未选任务、跨账号、非购物任务或版本不符时，明确提示或 404/409；模型无权从任意文本选择身份、URL、其他人的 task 或自己创造资源 ID。创建新购物任务仍可使用 013 显式表单，014 不实现自由文本自动跨任务创建。
2. **处理本轮输入**：只对所选购物 task 解析“补充条件/修改条件/继续查询/要求说明/歧义”，允许沿用一次结构化模型判断加服务端 schema 校验。刚追问人数时的“25 人”应关联这道待答问题；没有可靠上下文的“25”不得猜成人数或数量。用户明确条件的变更形成新的完整 `TaskRevision`，未提及字段沿用原快照；“这个取消了？”等歧义文本不得执行取消、删除或下单。纯普通聊天或不支持场景可返回有限说明，不强行调用购物 MCP。
3. **消息与 Run 绑定**：提交请求须以数据库唯一约束和请求指纹实现幂等：同一 owner/对话/`client_turn_id` 同内容、所选 task、预期版本的重试返回同一轮及原 Run；同键不同请求返回 409。用户消息只写一次；条件修订、Run 创建与链接采用事务或可恢复的阶段状态，不得出现“已显示用户消息但后台悄悄丢失应启动的 Run”且无法查询/恢复。既有 005 手工消息接口和 007–013 Run API 保持兼容。
4. **真实回复**：Worker 使用提交时绑定的用户消息和条件快照，不只读取固定 task.goal；上下文只取当前用户/当前任务必要的近几条消息与最近的待答问题，不能把整段会话或别的任务输入交给 Agent。一个完成的 Run 至多生成一条关联该 Run 的 `assistant` 消息；写入 Run 结果、终态及可重读回复时保证一致和幂等。追问也保存为助手消息；失败/取消只展示状态，不伪造成功回复。旧购物 Run 的历史结果不回填虚构助手消息。
5. **网页体验**：在 013 的任务工作台中增加已选任务下的消息输入与历史，显示用户、助手文本和对应 Run 状态/来源；保留显式任务/条件操作供检查。发送后从服务端恢复消息与 Run，SSE 断线按现有游标补读；重复点击与重试复用同一 `client_turn_id`。不要把“手工添加消息”误显示成已执行 Agent 的回合。回复作为文本渲染，模拟商品与未知报价继续标记。
6. **预算与工具**：沿用 012 的单次委派与至多一次 `shopping:search_products` MCP 查询；新增的结构化解析计入本轮模型请求和总时限，首版设**最多 5 次模型请求、1 次 MCP 业务查询**的共享硬上限并观测实际次数。若当前图/Worker 无法在该上限内完成，先记录原因和调整提案，不无界扩容。不允许引入采购规划 Agent、地图、其他 MCP、RAG 或订单写工具。

## 4. 持久化与故障语义

- 由实际建模决定使用 `conversation_turns` 或在现有 `messages`/`runs` 增加受约束的关联字段；明确唯一键、外键级联、旧记录兼容、assistant role 只能由服务端写入。所有正式字段通过新 Alembic 迁移，不改历史迁移，避免单靠前端数组拼接表现为已持久化。
- 对同步解析阶段设明确超时；若请求已受理但路由或创建 Run 未完成，保存可查询的 pending/failed 状态并支持同键恢复或可解释的安全失败。网络断开/前端超时后重试同一个请求 ID，不在未知状态下生成新键。两个并发更新同一 revision 只能有一个成功，失败者能看到当前 revision；取消、失租、旧 Worker 的迟到写入不得生成幽灵助手消息。
- 012 当前无图 checkpointer，本轮通过**新的用户回合和任务版本**继续追问，不声称原图节点暂停/续跑。若采用持久化待答状态，须绑定 owner、task 和所问字段，并明确多设备/话题切换时如何清除；遇到歧义必须追问，不可擅自写入条件。以后真正跨中断恢复图状态再独立设计。
- 不重复保存完整 MCP 原文或密钥；数据库中的消息、任务版本、Run 与结果随所属用户权限读取。未来 P3 的金额复算、候选/方案表、Skill 加载不在本任务中实现。

## 5. 执行顺序

1. 确定最小 `turn` 契约、请求指纹、消息/Run 关联和迁移，先做并发/重复请求与存量旧记录兼容验证；核对 013 保留的测试账号和数据，勿误删用户数据。
2. 实现“显式 task + 新消息 → 条件判定/修订 → 版本绑定 Run → Worker 看见本轮消息 → 助手回复”的服务端链路，保持旧消息和旧 `shopping_agent` API 正常。
3. 增加网页聊天输入与消息/状态重读；服务端身份和任务关联为准，前端不直接决定条件归属。
4. 在隔离账户、项目 PostgreSQL、真实 DeepSeek、真实 shopping-mcp 和浏览器中验证至少一个追问/补充条件的两轮过程；测试失败、空结果、重复请求和双用户隔离；使用后按规则清理**本轮新建**的隔离数据，不删除 013 已保留的记录或项目卷。
5. 更新 REST/消息契约、开发指南、执行报告、进度和任务索引。报告写明模型/工具真实调用次数、迁移、SSE 和哪些路径只是替身验证。

## 6. 验收

| 场景 | 通过标准 |
| --- | --- |
| 两轮购物对话 | 同一显式 shopping task：缺人数产生可读追问；用户答“25 人”后产生新 revision 和新 Run，Agent 基于明确的 25 人与本轮消息作答；刷新后用户/助手消息、revision、Run 可重读 |
| 幂等与并发 | 同键同请求只保存一轮/一条用户消息/一个 Run；同键异请求 409；两个并发版本更新至多一个成功；成功提交但丢失响应时同键重试不创建第二个 Run；外部调用后崩溃仍可能重复请求，不能承诺 exactly-once |
| 权限与真实性 | B 账户访问 A 的任务、消息、回复、Run/结果均为 404 或不可见；无授权字段不可写；无 MCP 查询不声称查到商品，空结果/模拟来源准确 |
| 故障与恢复 | 缺 Key、MCP 离线、解析失败、Worker 失租、取消、浏览器断线各有明确可重读状态，不能留下幽灵 assistant 回复；无自动订单/支付行为 |
| 回归 | 005 消息、006 task revision、007–013 Run/网页路径继续可用；真实 PostgreSQL 迁移与 `alembic check`、Python 测试/Ruff、前端 lint/build、相关 Java 构建通过；至少一次真实模型/MCP/浏览器两轮链路通过 |

真实服务不能运行时明确记录未验证项，不把 012/013 的历史闭环代替 014 的两轮证据。现有 013 报告将独立 HTTP 客户端 SSE 补读与真实浏览器测试分开，本轮也按同样边界报告，不把只通过 curl 的检查称为浏览器自动重连验收。
